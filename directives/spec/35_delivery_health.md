# 35 — Delivery health: sent vs delivered, last activity per channel, silence alert

**Status:** built and tested locally 2026-10-01; deploy pending Kes's go-ahead.

## Problem (Ali, 2026-10-01)
The SMS workflow matched nothing for a month while "attempted" looked healthy and email kept flowing. Controls must be: per channel (not one number), on **delivered** (not attempted), and a **scheduled check for silence** (a dead channel throws no error). ## Sources of truth
| Channel | "Sent" (hand-off) | "Delivered" |
|---|---|---|
| SMS | Cora wrote `Support issue Ticket #4` (recorded in `channel_events` kind `handoff`) | GHL message status `delivered` (Twilio status); `undelivered`/`failed` = failed, with the Twilio error (e.g. 30003 unreachable) |
| Email | Cora wrote `Support Issue Ticket #2` + Message | GHL email status behind `meta.email.messageIds[0]` (`GET /conversations/messages/email/{id}`, header 2021-04-15): delivered / opened / clicked = delivered; bounced / failed = failed |
| Calls | completed `launch_outbound_call` job | matching `call_events` row (Synthflow logs reach Cora 10–15 min later): voicemail, human_goodbye, human_pick_up_cut_off, agent_goodbye, or "undefined" with ≥5 s = connected; anything else = failed |

A hand-off matches a delivery for the same contact + channel within [-2 min, +60 min] (calls: +90 min). **Not confirmed** = hand-off older than 15 min (calls 25 min) with no delivery/failure record — the dead-workflow signature. Hand-offs are recorded for follow-ups and corrections (not counted before 2026-10-01 deploy; GHL-side deliveries are backfilled 72 h).

## Replies (inbound)
`delivery_sync` also reads inbound SMS / email / call messages from GHL conversations: logged in `channel_events` kind `reply`, and SMS/email replies are stored in `inbound_messages` (previously never written — so a STOP reply was invisible to Cora's own `_has_stop_reply` check). `lead_state.last_replied_at` is intentionally NOT changed (spec/06: reply handling is owned by GHL automations); only logged. Inbound calls are logged as reply events (they arrive via GHL, not Synthflow).

## Rules (`app/core/channel_health.py`, same for tile colour and alert)
* RED: no delivery for ≥ `channel_silence_hours` (60 = 2.5 days), or ≥20 sent in 24 h with <50 % delivered, or ≥20 sent, >10 % unconfirmed and nothing delivered/failed.
* AMBER: silent ≥ 36 h, delivered rate < 90 %, or >10 % unconfirmed.
* GREY: muted on purpose (`channel_silence_muted`, system paused, calls with outbound campaigns paused) — shown, never alerts.
* A brand-new tracker is not judged until its data covers the silence window (backfill 72 h satisfies this).

## Scheduled check
`alerting.evaluate_alerts` (60 s metrics cycle) calls `delivery_sync.sync` (throttled 5 min, time-boxed 20 s, resumable backfill) and `channel_health.run_silence_check` (hourly). A RED channel raises one `alert_events` row (`channel_silence_<channel>`) and ONE email to `alert_email_to` cc `channel_silence_cc` (default ali@colaberry.com); a recovery email when it clears. Read-only against GHL.

## Dashboard
Tile **Delivery Health** (`/delivery-health`, API `GET /dashboard/delivery-health[/{channel}]`): per-channel sent / delivered (%) / not confirmed / failed / last delivered / 7-day trend, Replies row, drill-down of failed + unconfirmed (contact ids, reasons). Home tile shows the delivered % per channel and a RED count.

## app_config keys
`channel_silence_hours` (60) · `channel_silence_amber_hours` (36) · `channel_silence_cc` · `channel_silence_muted` (comma list: email,sms,call) · `delivery_confirm_minutes` (15) · `delivery_sync_interval_seconds` (300) · `delivery_sync_backfill_hours` (72).

## Limits
* Email "delivered" = provider accepted/delivered, not read. Call "delivered" = connected, not conversation quality.
* Native GHL automations' emails/SMS count toward "last delivered" (the channel works) but not "sent" (no Cora hand-off).
* Needs `ghl_conversations_api_key` (already configured).

If `app_config.offer_forbidden_terms` is set it REPLACES the default list (it is never merged), so a staged rollout can set it to the default list minus `free` and delete it when GHL is clean.

**Exemptions (added 2026-10-12; remove course-name hits only - an employment / placement claim is always flagged):**

Basis: the inbox manager (InboxGenius) SMS / email notices never name the job title (fixed phrase "for the position you applied for"; employer names with a flagged term become "the employer"); the voice call names the position but calls are never scanned; an approver-edited email is also blocked by InboxGenius's send-time audit for any listed title. - *Offer or not (judge, rewritten 2026-10-14, Kes):* when every hit is a course name (not an employment / placement claim and not the word "free"), `app/services/content_judge.py` asks an LLM (`openai_model_content_audit`, JSON output) ONE question about the whole message in context: does it OFFER a retired course? Verdicts: `offers` (promotes, describes as available, prices, schedules, invites, or says Colaberry teaches that subject), `not_offering` (a refusal, an explanation of the move to the AI program, a quoted caller, a job title, a contrast with the old course that offers nothing) or `unclear`. ## SMS opt-out guard (added 2026-10-16)
GoHighLevel locks a sub-account's texts for 24 hours at a 3% opt-out rate (10% delivery errors). It did on 2026-10-15 (11 opt-outs on ~230 texts) and every text failed until 17:45 CT the next day; GHL marks a failed workflow SMS "Success" and does not retry, so the leads were silently dropped. `app/services/sms_guard.py` watches the same ratio and pauses Cora's own texts first.
- **Rate (rolling 24 h):** opt-outs by SMS reply (`optout_actions`: source `sms_reply`, kind `dnd`, status `applied`) / texts GHL reports delivered (`channel_events` kind `delivery`, channel `sms`, outcome `delivered`).
- **Pause** at >= `sms_guard_pause_pct` (default 2.0) with at least `sms_guard_min_sample` texts (default 50); **resume** below `sms_guard_resume_pct` (default 1.5), or when too few texts remain to judge AND at most `sms_guard_resume_max_optouts` (default 1) opt-outs are left in the window (a lockout that makes texts fail shrinks the delivered count; 2 opt-outs on 44 texts is not "too few to judge"). State in `app_config.sms_guard_state` (ok | paused), evaluated every alert cycle; `sms_guard_enabled=false` switches it off.
- **Effect:** while paused, `sms_ledger.reserve` BLOCKS source `followup` (Cora's post-call texts; code `optout_guard`). The lead still gets the email / voice cadence. Texts sent by GHL workflows or staff are outside Cora's control and are NOT stopped. Replies to a lead who texts us are unchanged.
- **No alerts (Kes 2026-10-16):** a pause or resume raises no dashboard alert and sends no email; it is an `app_config` change (audit_log, updated_by "auto: sms opt-out guard") plus a log line.
- Tests: `tests/unit/test_sms_guard.py`, `tests/unit/test_sms_gate.py` (guard blocks follow-ups only).

## Recovery rule for the delivered-rate alert (added 2026-10-16)
The "< 50% of resolved delivered in 24 h" rule lagged after an outage: GHL's SMS lockout ended 17:45 CT and a text delivered at 17:56, but `channel_silence_sms` stayed RED for hours because the 24 h window still held the failures. Now, when the last `recovery_hours` (3) hold at least `recovery_min_resolved` (5) resolved sends delivered at >= `recovery_rate` (0.9), the rate rules downgrade to AMBER ("recovering: ...") and the alert resolves. Too few recent sends = no recovery claim, so a quiet channel stays RED until it proves itself. Test: `test_a_recovered_channel_stops_alerting_before_the_24h_rate_rolls_off`.
A quiet recovered channel stays recovered: no failure in the last `recovery_hours` AND the newest delivery is later than the newest failure also counts (the alert resolved at 19:51 CT on 2026-10-16 and re-fired at 23:35 CT only because nothing was sent overnight, so the 3 h window was empty). A failure after the last delivery, or inside the recent window, is not recovery.

## Voice-call audit (AI Receptionist) and alert origin labels (Kes 2026-10-20; built on branch feat/voice-call-audit, pending merge/deploy)
**Why:** the audit above reads only texts and emails ("calls are never scanned"). On 2026-10-15 GHL's AI Receptionist (Voice AI agent, inbound) told a caller who asked for a SQL developer course that he could enroll in it, quoted a retired "$49 AI Career Readiness Starter ... SQL Server installation", used "free" and the old `myfreeaiclass.com` domain - none of it seen by Cora. Cause: the agent's `knowledge_base` action still holds the retired program content; its prompt has no retired-course rule.
**Source of truth for the scan:** GHL Voice AI call logs, not the contact Note. `GET /voice-ai/dashboard/call-logs?locationId=&contactId=` (works with the Private Integration token, not the conversations-scoped token) returns `transcript` (one string, lines prefixed `human:` / `bot:`), `summary`, `executedCallActions` (e.g. KNOWLEDGE_BASE), `agentTransferOccurred`, `createdAt`, `duration`. The Note GHL writes ("AI Call with: AI Receptionist") holds only the summary and extracted fields, so it cannot show what the agent said.
**Scan rule:** apply `offer.forbidden_hits` to the `bot:` lines only. A caller saying "SQL" is not a violation; the agent offering, pricing or confirming it is. Retired-course hits go through the same offer/not-offering judge as texts; "free" (outside the approved link) and employment claims are always flagged.
**Built (code):** `app/core/voice_audit.py` (pure: transcript parse, bot-only scan, spoken approved link "training dot colaberry dot com slash start dash free", origin labels), `app/services/voice_audit.py` (reads `GHLClient.list_voice_call_logs`, newest first, 48 h window; writes `channel_events` channel `voice`: `content_flag`, `content_ok`, `voice_seen`; runs inside the alerting cycle), `channel_health._flag_line` (alert wording). Tests: `tests/unit/test_voice_audit.py`.
**How it behaves:** a call is scanned once (`voice_seen` / `content_flag` row per call-log id), so replays never alert twice. A course-name-only hit goes to the same offer/not-offer judge as texts (any doubt or error stays flagged); `free` outside the approved link and employment claims are never judged away. A call with no transcript is retried for 2 h, then marked scanned (no_transcript). Only the agent's `bot:` lines count. Switch off with app_config `voice_audit_enabled=false`.
**Every content-flag alert line ends with its origin:** voice -> `[origin: GHL AI Receptionist (voice call) - fix its prompt / knowledge base in GHL Voice AI]` (other Voice AI agents: `GHL Voice AI agent ...<last 6 of id>`; the Receptionist's id is in `KNOWN_AGENTS`); text / email -> `[origin: GHL <channel> with source '<source>' ...]`. Not yet distinguished: Cora engine vs Conversation AI bot for source `app` texts.
**If the audit itself breaks** it raises ONE `ghl_voice_audit_error` alert ("AI Receptionist call audit could NOT read GHL Voice AI call logs: <error> ... not a problem in the AI Receptionist itself"; usual cause: the Private Integration token lost its Voice AI read scope) and resolves it on the next good read. Nothing is marked clean after a failed read.
**Dry run on production (2026-10-20, read-only):** 216 call logs, 210 with transcripts, 13 would flag (5 "free", 1 "job placement", 1 "sql"+"free" = the Abere call, 6 course-name-only that the judge decides). Voice flags still email `alert_email_to` like text flags (same alert).
